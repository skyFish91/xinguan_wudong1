## 1. 架构决策记录（ADR）

| 编号 | 决策 | 选择 | 理由 |
|------|------|------|------|
| ADR-1 | 架构形态 | 模块化单体 | 需求书 4.1 微服务图标注"建议"；6 天课程内单体可交付、可演示、可测试，模块边界清晰保留拆分可能 |
| ADR-2 | 后端框架 | Midway（Node.js + TS） | 课程技术主线指定 |
| ADR-3 | ORM | TypeORM | Midway 官方配套，参数化查询防 SQL 注入 |
| ADR-4 | 前端 | Vue 3 + Vite + Element Plus + Pinia | 课程主线指定 Vue，Element Plus 生态成熟 |
| ADR-5 | 认证 | JWT 双 token（access 2h + refresh 7d），bcrypt | 前后端分离标准方案，满足安全需求 |
| ADR-6 | 支付 | 模拟微信支付 | 需求书允许；无商户资质，二维码模拟页 + 回调 |
| ADR-7 | 文件存储 | 本地磁盘 + 静态服务 | 需求书 4.3 明确"上传到本地磁盘" |
| ADR-8 | 缓存 | Redis（Docker 容器） | 课程主线；热点数据 + 验证码 + 库存预扣 |
| ADR-9 | 部署 | Docker Compose 单机编排 | 课程主线；MySQL 用本机服务，应用+Redis 容器化 |
| ADR-10 | 终端范围 | PC Web + 管理后台 | 小组确认不做小程序端 |

## 3. 后端模块设计（server/）

### 3.1 目录结构

```
server/
├── src/
│   ├── config/             # 配置（数据库/Redis/JWT/上传）
│   ├── middleware/         # 全局中间件（鉴权、日志、错误、脱敏）
│   ├── common/             # 统一响应、错误码、装饰器、DTO 基类
│   ├── module/
│   │   ├── auth/           # 注册/登录/refresh/验证码
│   │   ├── user/           # 个人中心、收货地址、收藏聚合
│   │   ├── merchant/       # 商家入驻申请、商家账号
│   │   ├── upload/         # 图片/视频上传（本地磁盘）
│   │   ├── message/        # 站内消息中心
│   │   ├── search/         # 统一搜索
│   │   ├── cart/           # 统一购物车
│   │   ├── order/          # 统一订单中心（5 类订单状态机）
│   │   ├── pay/            # 模拟微信支付
│   │   ├── clothing/       # 模块一 衣：分类/商品/SKU/评价
│   │   ├── food/           # 模块二 食：餐厅/餐位/农产品
│   │   ├── hotel/          # 模块三 住：民宿/房型/房态日历
│   │   ├── travel/         # 模块四 行：景区/票种/路线/电子票
│   │   ├── community/      # 模块五 社区：游记/评论/话题/关注
│   │   └── admin/          # 模块六 后台：用户/商家/财务/看板/运营
│   ├── entity/             # TypeORM 实体（按模块划分）
│   └── schedule/           # 定时任务（订单超时关闭、房态生成）

└── package.json
```

### 3.2 统一响应与错误码

```json
{ "code": 0, "message": "success", "data": {} }
```

错误码分段：1xxx 认证、2xxx 参数、3xxx 业务、5xxx 系统。全局异常过滤器统一捕获。

### 3.3 鉴权设计

- JWT payload：`{ userId, role: 'user' | 'merchant' | 'admin', merchantType? }`
- 中间件：`@Auth()`（登录用户）、`@Auth('admin')`（管理员）、`@Auth('merchant', 'clothing')`（指定模块商家）
- Refresh 策略：access 过期后前端自动用 refresh token 换新，无感续期

## 4. 数据库设计要点

- 统一 `t_` 前缀，共 60+ 表，按 8 个领域分组：用户域、商品域、餐饮域、住宿域、票务域、社区域、平台域、订单支付域
- 关键设计：
  - `t_order` 主表 + `t_order_item` 明细，`order_type` 区分 5 类订单
  - `t_room_inventory` 房态日历：`(room_id, date)` 联合唯一，预扣/释放保证并发安全
  - `t_ticket_inventory` 票务库存：按 `(ticket_id, use_date)` 分日期库存
  - `t_sku` 商品 SKU 库存，下单时条件更新 `WHERE stock >= n` 防超卖
  - 点赞/关注/收藏用 `(user_id, target_id, target_type)` 联合唯一
  - 详情见 `docs/12-数据库设计文档.md` 与 `sql/01-ddl.sql`

## 6. 核心流程设计

### 6.1 下单支付（商品类）

```
加购 → 购物车/立即购买 → 锁库存（SKU 条件更新）→ 创建订单(待支付)
→ 模拟支付页（二维码）→ 点击"模拟扫码支付" → 支付成功回调
→ 订单已支付 → 商家发货 → 物流 → 确认收货 → 已完成
超时 30 分钟未支付 → 定时任务关单 + 回补库存
```

### 6.2 预订类（餐位/住宿/门票/路线）

```
选择日期/时段/房型/票种 → 校验可订（房态日历/分日期库存/时段余量）
→ 预扣 → 创建订单(待支付) → 模拟支付 → 已支付/待确认 → 商家确认 → 进行中 → 完成
住宿订单支付后生成入住码；门票/路线支付后生成电子票二维码
```

### 6.3 内容审核

```
发布游记 → 敏感词过滤 → 命中进入待审核 → 管理员通过/拒绝（拒绝填原因）
→ 通过后进入信息流；3 次违规自动禁言 24h
```

## 7. Redis 缓存设计

| Key | 用途 | 过期 |
|-----|------|------|
| `hot:products` | 首页热门商品 | 5min |
| `product:detail:{id}` | 商品详情 | 10min |
| `food:restaurants:list` | 餐厅列表 | 5min |
| `hotel:rooms:{roomId}:{date}` | 房态库存预扣 | 30min |
| `sms:code:{phone}` | 验证码 | 5min |
| `search:hot` | 热搜词 | 1h |
| `travel:routes` | 路线套餐列表 | 5min |
| `community:feed` | 社区推荐流 | 5min |

库存预扣采用 Redis 原子操作 + 数据库兜底。证据记录见 `docs/08-Redis缓存证据.md`。

CI/CD：GitHub Actions —— push 触发 → 单测 → 构建镜像 → 推送 → compose 部署，流水线记录见 `docs/10-CICD流水线记录.md`。

## 9. 安全设计

- bcrypt 密码哈希；JWT 签名密钥环境变量
- TypeORM 参数化查询防注入；富文本 DOMPurify 白名单防 XSS
- 手机号/身份证脱敏展示；上传文件类型/大小校验
- 关键操作（退款、封禁）二次确认 + 操作日志全记录

## 10. 可扩展性预留

- 模块目录边界清晰，可平滑演进为微服务（拆分 service 为独立进程）
- 支付层抽象 `PayProvider` 接口，未来可接真实微信支付
- 上传层抽象，未来可切 OSS
- 国际化预留 i18n 结构（当前仅简体中文）
