## 一、设计概述

### 1.1 技术选型

| 项目 | 选择 | 说明 |
|------|------|------|
| 数据库 | MySQL 8.0 | 库名 `wudong`，DDL 见 `sql/01-ddl.sql` |
| 存储引擎 | InnoDB | 支持事务、行级锁、条件 UPDATE 防超卖 |
| 字符集 | utf8mb4（utf8mb4_general_ci） | 完整支持中文与 emoji 字符存储 |
| ORM | TypeORM（Midway 配套） | 实体定义见 `server/src/entity/` |
| 支付 | 模拟微信支付 | 渠道标识 `mock_wxpay`，无真实商户资质 |

### 1.2 命名与通用约定

| 约定 | 规则 | 说明 |
|------|------|------|
| 表名 | `t_` 前缀 + 蛇形小写单数 | 如 `t_order_item`、`t_meal_quota` |
| 字段名 | 蛇形小写 | 如 `order_no`、`created_at` |
| 主键 | `id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT` | 全部自增，避免分布式 ID 依赖 |
| 时间戳 | `created_at` / `updated_at DATETIME` | 默认 `CURRENT_TIMESTAMP`；`updated_at` 额外 `ON UPDATE CURRENT_TIMESTAMP` |
| 软删 | 以 `status TINYINT` 状态字段实现 | 项目未采用 `deleted` 字段式软删；删除/下架/封禁均走状态标记，数据物理保留（如 `t_comment.status=0` 删除、`t_post.status=2` 已下架、`t_user.status=0` 封禁） |
| 外键 | 逻辑外键 + 索引 | DDL 不建物理 FOREIGN KEY 约束，关联一致性由应用层保证 |
| 索引命名 | `uk_`（唯一）、`idx_`（普通） | 如 `uk_order_no`、`idx_user` |
| 金额 | `DECIMAL(10,2)` | 订单金额、价格、佣金等 |
| 比例 | `DECIMAL(5,4)` | 佣金比例，如 0.05 |
| 评分 | `DECIMAL(2,1)` | 默认 5.0 |
| 经纬度 | `DECIMAL(10,6)` | 餐厅、民宿、景区定位 |
| 状态枚举 | `TINYINT` + COMMENT 枚举说明 | 所有状态字段注释内写明取值含义 |
| JSON / 富文本 | `TEXT` / `MEDIUMTEXT` | 图片列表、资质材料、权限标识、详情富文本等 |
| 快照 | 订单明细冗余快照 | `t_order_item` 保存成交时标题/规格/图片/单价，商家改价不影响历史订单 |
| 计数冗余 | 计数字段随操作增减 | `like_count`、`comment_count` 等冗余计数，配合唯一索引防重复 |

## 二、分域 ER 说明

### 2.1 用户域

- `t_user` 为统一账号表，游客 / 商家 / 管理员三端合一，以 `role`（user/merchant/admin）区分，`phone` 唯一；`status` 封禁、`ban_until` 禁言。
- `t_user_address`：`user_id` → `t_user.id`，一个用户多个收货地址，`is_default` 标记默认地址。
- `t_merchant`：`user_id` → `t_user.id`，商家账号与登录账号一对一；`module_type` 声明归属模块（clothing/food/hotel/travel），是衣、食、住、行四域业务资源的归属主体。
- `t_merchant_apply`：`user_id` → `t_user.id`，入驻申请审核流（0 待审核 / 1 通过 / 2 驳回），审核通过后落库为 `t_merchant`，`audit_admin_id` 记录审核管理员。
- `t_role`：RBAC 角色表，`permissions` 存权限标识 JSON 数组，管理端权限控制用。
- `t_operation_log`：`operator_id` → `t_user.id`，管理端操作留痕，按操作人、时间建索引。

### 2.2 商品域（衣）

- `t_product_category`：两级分类，`parent_id` 自关联（0 为一级分类）。
- `t_product`：非遗商品主表；`category_id` → `t_product_category.id`，`merchant_id` → `t_merchant.id`，`inheritor_id` → `t_inheritor.id`（可空，非遗传承人背书）；`price` 为 SKU 最低起售价、`stock` 为 SKU 库存汇总。
- `t_product_sku`：`product_id` → `t_product.id`，实际库存与成交价落在 SKU 层，防超卖操作对象。
- `t_product_image`：`product_id` → `t_product.id`，`sort` 控制轮播顺序。
- `t_inheritor`：非遗传承人资料，独立于商品存在，可被多商品引用。

### 2.3 餐饮域（食）

- `t_restaurant`：`merchant_id` → `t_merchant.id`，含经纬度、营业时间、容纳人数。
- `t_dish`：`restaurant_id` → `t_restaurant.id`，`is_signature` 标记招牌菜。
- `t_meal_slot`：`restaurant_id` → `t_restaurant.id`，时段模板（如午餐 11:30-13:30），`max_booking` 为单时段最大预订数。
- `t_meal_quota`：预订余量表，`restaurant_id + slot_id + booking_date` 三维联合唯一，`booked` 为已订桌数，与 `t_meal_slot.max_booking` 比对防超订。
- `t_farm_category` / `t_farm_product`：农产品分类与商品；`farm_product.category_id` → `t_farm_category.id`，`merchant_id` → `t_merchant.id`，含产地溯源、保质期字段。

### 2.4 住宿域（住）

- `t_homestay`：`merchant_id` → `t_merchant.id`，风格标签（木楼/吊脚楼）、设施标签、入住离店时间、押金等入住须知字段。
- `t_room_type`：`homestay_id` → `t_homestay.id`，基础价与同日期可售间数。
- `t_room_inventory`：房态日历，`room_type_id + inv_date` 联合唯一，按日动态定价、按日预扣（`booked` ≤ `total`），是住宿预订防超卖的核心表。

### 2.5 出行域（行）

- `t_scenic`：景区基础资料，含经纬度与开放时间。
- `t_ticket_type`：`scenic_id` → `t_scenic.id`，一景区多票种（成人票/儿童票/学生票/家庭套票），`valid_rule` 有效期规则。
- `t_ticket_inventory`：`ticket_type_id + use_date` 联合唯一，分日期库存（`sold` ≤ `total`），票务防超卖核心表。
- `t_route`：`merchant_id` → `t_merchant.id`，路线套餐（一日游/两日游/多日游），含出发地、目的地、住宿餐饮标准。
- `t_route_itinerary`：`route_id` → `t_route.id`，按 `day_no` 逐日行程（景点/用餐/住宿/交通）。
- `t_eticket`：电子票表；`order_id` → `t_order.id`，`ticket_order_id` → `t_ticket_order.id`，`biz_type/biz_id` 指向票种或路线，`code` 唯一即核销二维码内容，`verify_at/verify_by` 记录核销。
- `t_traffic_guide`：交通攻略静态内容（出发地/目的地/交通方式/时长/费用），无外键。

### 2.6 社区域

- `t_post`：游记；`user_id` → `t_user.id`，`topic_id` → `t_topic.id`（可空），`linked_type/linked_id` 软关联地点（restaurant/homestay/scenic），`linked_name` 存名称快照；`status` 审核流（0 审核中 / 1 正常 / 2 已下架），`published_at` 过审时间；`like_count/comment_count/favorite_count/view_count` 冗余计数，`is_hot` 首页推荐。
- `t_comment`：`post_id` → `t_post.id`，`parent_id` 自关联（0 为一级评论，否则为回复），`reply_user_id` 指向被回复用户，支持二级回复。
- `t_topic`：独立话题表，`name`（含#）唯一，统计关注数与帖子数。
- `t_follow`：关注关系，`user_id + follow_user_id` 联合唯一防重复关注。
- `t_like`：点赞，`user_id + target_type + target_id` 联合唯一，`target_type` 为 post/comment。
- `t_report`：举报，`report_user_id` → `t_user.id`，`target_type/target_id` 指向被举报的游记或评论，`status` 处理流（0 待处理 / 1 已处理(删除) / 2 已驳回）。

### 2.7 订单/支付域

- `t_order`：统一订单主表，一张表承载 5 类订单（`order_type`：goods/meal/hotel/ticket/route）；`user_id` → `t_user.id`，`merchant_id` → `t_merchant.id`（有则关联）；`order_no` 唯一，`status` 八态状态机（见 4.2）。
- 扩展子表与主表 1:1（各以 `uk_order(order_id)` 唯一约束保证）：
  - `t_order_item`：goods 类明细，`sku_id`（模块一 SKU）与 `farm_product_id`（模块二农产品）二选一，含快照与发货状态、物流单号；
  - `t_meal_booking`：meal 类扩展，`restaurant_id`、`slot_id`、`booking_date`、人数与联系人；
  - `t_hotel_booking`：hotel 类扩展，`homestay_id`、`room_type_id`、入住离店日期、入住人实名与入住码 `checkin_code`；
  - `t_ticket_order`：ticket/route 类扩展，`biz_type/biz_id` 指向票种或路线，`use_date`、数量与游客信息 JSON。
- `t_pay_record`：`order_id` → `t_order.id`，`pay_no` 唯一；一笔订单可多次支付尝试（0 待支付 / 1 成功 / 2 失败），以最终成功记录为准。
- `t_refund_record`：`order_id` → `t_order.id`，`refund_no` 唯一，状态 0 申请中 / 1 已退款 / 2 已驳回，`handle_note` 处理备注。
- `t_cart_item`：`user_id` → `t_user.id`，`sku_id/farm_product_id` 二选一，统一购物车。

### 2.8 平台域

- 运营位：`t_announcement`（公告）、`t_banner`（首页轮播图）、`t_activity_banner`（活动横幅）、`t_recommend`（推荐位，`slot_name` 推荐位名称 + `biz_type/biz_id` 指向 product/post/restaurant/homestay/route）。
- `t_message`：`user_id` → `t_user.id`（接收用户），`msg_type` 区分 system 系统 / order 订单 / interact 互动。
- `t_system_config`：`config_key` 唯一，承载佣金比例与结算周期等运行参数（`commission_goods`、`commission_service`、`settlement_cycle`，见 4.4、4.6）。
- `t_sensitive_word`：敏感词库，`word` 唯一，内容安全过滤用。
- 财务链：`t_finance_record`（`order_id` → `t_order.id`，`merchant_id` → `t_merchant.id`，支付成功后逐单记账，`settle_no` → `t_settlement.settle_no`）→ `t_settlement`（`merchant_id` → `t_merchant.id`，按周期汇总生成结算单，0 待打款 / 1 已打款）。
- 数据类：`t_visit_log`（PV/UV 埋点，`user_id=0` 为匿名）、`t_search_history`（`user_id` → `t_user.id`）、`t_hot_keyword`（热搜词，`keyword` 唯一）。

## 四、设计要点

### 4.1 统一订单模型

一张 `t_order` 主表承载 5 类订单（goods/meal/hotel/ticket/route），以 `order_type` 区分；各类订单的业务差异字段下沉到扩展子表，每个子表通过 `uk_order(order_id)` 唯一约束保证与主表 1:1：

| order_type | 扩展子表 | 关键业务字段 |
|---|---|---|
| goods | t_order_item | 快照、数量、发货状态、物流单号 |
| meal | t_meal_booking | 时段、预订日期、人数、联系人 |
| hotel | t_hotel_booking | 房型、入住离店日期、实名、入住码 |
| ticket/route | t_ticket_order | 票种/路线、使用日期、游客 JSON |

`merchant_id` 在主表（有则关联），便于按商家聚合订单与财务。

### 4.2 订单状态机

`t_order.status` 为 TINYINT 八态（注释见 3.2.1）：

| 状态值 | 名称 | 说明 |
|---|---|---|
| 0 | 待支付 | 下单未支付，超时可取消 |
| 1 | 已支付待确认 | 支付成功，待商家/系统确认 |
| 2 | 已确认 | 商家已确认 |
| 3 | 进行中 | 履约中（如已发货、入住中、待出行） |
| 4 | 已完成 | 履约完成，可评价 |
| 5 | 已取消 | 取消终态 |
| 6 | 退款中 | 发起退款申请 |
| 7 | 已退款 | 退款成功终态 |

典型流转：0 → 1 → 2 → 3 → 4；取消分支 0/1 → 5；退款分支 2/3/4 → 6 → 7。退款申请落在 `t_refund_record`（0 申请中 / 1 已退款 / 2 已驳回），退款成功（含驳回）时同步回写主表状态。状态变更同时更新 `updated_at`，服务层实现以实际代码为准。

### 4.3 库存防超卖（条件 UPDATE）

四类库存全部采用"条件 UPDATE + 受影响行数校验"防超卖，不依赖先查后改：

| 库存维度 | 表 | 扣减方式 | 并发保护 |
|---|---|---|---|
| 商品 SKU 库存 | t_product_sku.stock | `UPDATE t_product_sku SET stock = stock - n WHERE id = ? AND stock >= n`，受影响行数 = 0 则库存不足 | 行级锁；t_product.stock 为 SKU 汇总，随 SKU 同步 |
| 农产品库存 | t_farm_product.stock | 同上条件 UPDATE | 行级锁 |
| 房态日历 | t_room_inventory（total/booked） | `UPDATE ... SET booked = booked + n WHERE room_type_id = ? AND inv_date = ? AND booked + n <= total AND status = 1` | uk_room_date(room_type_id, inv_date) 唯一防重复行 |
| 票务库存 | t_ticket_inventory（total/sold） | `UPDATE ... SET sold = sold + n WHERE ticket_type_id = ? AND use_date = ? AND sold + n <= total AND status = 1` | uk_ticket_date(ticket_type_id, use_date) 唯一防重复行 |
| 餐位余量 | t_meal_quota.booked | `booked + n <= t_meal_slot.max_booking` 校验后条件 UPDATE | uk_rest_slot_date(restaurant_id, slot_id, booking_date) 唯一防重复行 |

订单取消或退款成功后按原路径回补库存（减扣反向加回）。条件 UPDATE 依赖 InnoDB 行级锁，在并发下单时天然串行化，是防超卖的核心机制。

### 4.4 佣金记账

- 支付成功后生成一条 `t_finance_record`：`order_amount` 为订单金额，`commission_rate` 为平台抽佣比例，`commission = order_amount × commission_rate`，`merchant_income = order_amount − commission`。
- 比例按订单类型从 `t_system_config` 读取（初始数据见 `sql/02-dml.sql`）：

| 配置项 | 值 | 说明 |
|---|---|---|
| commission_goods | 0.05 | 实物商品平台抽佣比例（goods 类，含农产品） |
| commission_service | 0.10 | 服务类（民宿/门票/餐位/路线）抽佣比例 |

- 记账后 `settle_status = 0`（未结算），待结算周期处理（见 4.6）；退款成功后需按退款金额冲减对应财务记录或生成冲销记录（以服务层实现为准）。
- `t_merchant.settle_status` 与财务记录结算状态同步。

### 4.5 电子票

- 票务/路线订单（ticket/route）支付成功后，按 `t_ticket_order.quantity` 逐张生成 `t_eticket`，每张电子票 `code` 唯一（即电子票号/二维码内容），`visitor_name` 从游客信息 JSON 落库。
- 核销：验票时校验 `use_date` 与 `status = 0`，核销后置 `status = 1` 并记录 `verify_at`（核销时间）、`verify_by`（核销人）。
- 退款：退款成功后电子票置 `status = 2`（已退款），对应票务库存回补（4.3）。

### 4.6 结算（T+7）

- 结算周期由 `t_system_config.settlement_cycle = 'T+7'` 配置（即订单完成 7 天后进入结算池）。
- 结算流程：按商家汇总周期内 `settle_status = 0` 的 `t_finance_record` 生成 `t_settlement` 结算单（`settle_no` 唯一，`period_start/period_end` 为结算周期），`status` 0 待打款 → 1 已打款；打款完成后回写 `t_finance_record.settle_status = 1` 并填 `settle_no`，同步 `t_merchant.settle_status`。

### 4.7 快照与冗余计数

- 快照：`t_order_item` 保存成交时的商品标题、规格、图片、单价快照，商家后续改价、换图不影响历史订单展示。
- 冗余计数：`t_post.like_count/comment_count/favorite_count/view_count`、`t_comment.like_count`、`t_topic.follow_count/post_count`、`t_product.sales`、`t_route.sales` 均为冗余计数，随操作事务内增减，避免高频 COUNT 查询；`t_like`、`t_follow` 的联合唯一约束保证同一用户不可重复点赞/关注。
- 统一互动：评价（`t_review`）、收藏（`t_favorite`）以 `biz_type + biz_id` 多态关联各域业务对象（product/farm/restaurant/homestay/ticket/route/post），一套表覆盖衣、食、住、行、社区五个模块。
